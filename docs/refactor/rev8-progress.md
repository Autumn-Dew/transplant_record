# 第八轮修正 — 四个实际使用中的问题

> 本轮全部来自真实使用反馈，并**用你机器上的真实数据**（`F:\Tencent Message2\代肝记录\代肝记录\data`，
> 只读副本）复现与验证，没有改动那份数据本身。

## 1. 问题与根因

| # | 现象 | 根因 |
|---|---|---|
| 1 | 新建项目的游戏与原来的游戏项目**id 不一致** | 老数据（v1.0.42）里 `game` 存的是**游戏名**（`终末地`/`明日方舟`），新建项目存的是**游戏 id**（`endfield`/`ak`）。同一个游戏在数据里变成两种值 → 游戏筛选出现两个同类 chip、价格表按 id 匹配时对不上 |
| 2 | **删掉的托管仍会出现续费窗口** | 删除时若该项目已有执行记录，会转为「归档」（只打 `archived` 标记，`state` 仍是 `active`）；而续费候选 `findRenewalCandidate()` 只比较 `state`，没有检查 `archived` → 归档项目仍被当成可续费项目 |
| 3 | **无法修改代肝天数（尤其减少）** | ① 上一轮把「保存」也纳入了 4 次点击确认，点一次看起来没保存；② 「新增记录」编辑态没有把 `host.cycleDays` 回填到「托管天数」输入框，框是空的；③ 改天数时只重算了周期天数，没重算计划次数（减少天数后「已完成 / 计划」会不自洽） |
| 4 | 需要参考真实数据 | 用上面的真实数据做了只读分析 + 全量迁移演练 |

## 2. 修复

### 2.1 游戏 id 统一（问题 1）

`runStartupMigration()` 新增一步：把每个项目的 `game` 规范化为**游戏目录里的 id**
（找不到对应游戏的——例如游戏已被删除——原样保留），`gameName` 保持展示名不变。

* 只改 `game` 一个字段，**其余字段零改写**（真实数据实测：72 个项目、除 `game` 外被改写字段数 = 0）
* 幂等：第二次启动 `gamesNormalized = 0`

### 2.2 归档项目不再是续费候选（问题 2）

`findRenewalCandidate()` 改为用 `isArchived()` / `isCancelled()` 判断（同时保留原来的 `state` 判断）：

```js
if (!isHosting(p)) return false
if (isArchived(p) || isCancelled(p)) return false   // ← 新增：归档标记也要排除
```

### 2.3 天数可改、可减（问题 3）

* **保存类按钮改回单击生效**（只有删除 / 归档 / 清除这类破坏性操作才是「连点 4 次」）：
  「新增记录」保存、蓝图保存 / 以此为基础新建、详情「保存」、详情「确认续费」都是单击即生效。
  破坏性操作仍然保留统一的多击确认与逐层音效。
* 「新增记录」编辑态把 `host.cycleDays` 回填到「托管天数」，并顺手把游戏字段规范成 id（下拉能正确选中）。
* `updateProject()` 改天数时同时重算 `plannedTimes`，且**不少于已完成次数**（避免「已完成 > 计划」）。

## 4. 语义调整（需要你确认）

上一轮的要求是「所有按钮保证多次点击机制」，本轮反馈「改不了天数」——矛盾点在于**保存被卡在 4 次点击**。
现在的划分是：

| 类型 | 机制 | 覆盖 |
|---|---|---|
| 破坏性 / 不可逆 | 连点 4 次 + 递进色 + 逐层音效 | 删除（项目/记录/蓝图）、归档、清除所有数据、确认完成、跳过今天 |
| 表单提交 | 单击即生效（表单本身已是二次确认） | 新增/保存记录、保存蓝图、以此为基础新建、详情保存、确认续费 |

若你希望连保存也要 4 次，一句话即可改回。
